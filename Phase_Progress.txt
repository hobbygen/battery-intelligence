Bug found and fixed during this phase (worth remembering):
- IHost starts hosted services SEQUENTIALLY in registration order, fully
  awaiting each StartAsync. BatteryPersistenceBridge was registered after
  BatteryMonitoringService, so BatteryMonitoringService's own startup refresh
  (and its first Updated event) could fire before the bridge subscribed —
  silently dropping the first reading. Fixed by having the bridge also pull
  IBatteryMonitoringService.CurrentSnapshots directly in its own StartAsync.
- Also fixed: App.xaml.cs was calling _host.Start() BEFORE settings.LoadAsync().
  Hosted services (BatteryMonitoringService's poll interval, DatabaseMaintenanceService's
  retention window) read ISettingsService.Current in their own StartAsync, so
  settings must load first. Reordered in OnLaunched.

Key deviations (see roadmap.md Phase 3 for full detail):
- BatterySample's per-row DataQuality/MeasurementSource is a REDUCTION from
  Core's per-field grading (schema only has one pair per row) — graded by the
  worst populated field, sourced from the percentage reading. Every consumer
  above the write queue still sees full per-field grading on the live
  BatterySnapshot; only the persisted row is coarser.
- Only MINUTE-level rollup ships. SampleHour/DailyStatistics tables exist but
  have no producer yet — deferred until Sessions (Phase 4) and Analytics
  (Phase 8) give them something worth summarising. MinuteRetentionDays/
  HourRetentionDays are read into DataRetentionSettings but not yet enforced.
- Validator matrix partially deferred: monotonic-timestamp guard and the
  awake-percentage-jump check need Phase 4's screen state to be meaningful.
- Backup-before-migration is implemented but has no automated test — nothing
  to migrate TO yet (only V001 exists). Will be exercised when V002 ships.

Key deviations (see roadmap.md Phase 4 for full detail — this list is long,
read the roadmap version if touching Sessions code):
- Sessions project is net10.0-windows now, not the plain net10.0 it was stubbed
  as in Phase 1 — but the STATE MACHINE (Core.Sessions) stays pure/net10.0.
  If you need to test session LOGIC, it's in Tests.Unit via Core; if you need
  to test the ORCHESTRATOR (hardware wiring), that's not yet covered by an
  automated test (only live-verified) — consider Tests.Simulation-style
  coverage if this needs hardening later.
- "Charging -> Idle" closing (transition table) vs. "pause/resume =
  interruption" (section 3) reconciled via a grace period: Idle-while-AC-on
  starts a timer; resume within 15 min = Interruption; exceeding it (or
  reaching 100%) = real close.
- Debounced session start is BACKDATED to the first sample of the confirmed
  streak, not the confirming sample — otherwise every session start time/pct
  understates reality by (debounce_count - 1) sampling intervals.
- Debounce count (3) unchanged, but at today's 30s battery-poll cadence that's
  ~90s to commit a rate-driven transition, not session-engine.md's assumed
  ~15s (which assumed Phase 5's 5s power-sampling cadence). Self-corrects when
  Phase 5 ships; no engine change needed.
- Reboot has no distinct inferred SystemEventKind — gap detection can't observe
  a reboot from inside a process that didn't survive it; crash recovery at
  startup (RecoverAsync) handles that case without needing to know why
  continuity broke.
- Timeline (ISessionStore.GetTimelineAsync) returns session spans + point
  markers for session/system events, NOT fully reconstructed contiguous
  screen-on/off spans (session-engine.md section 7's fuller example). The
  SystemEvent rows needed for that reconstruction ARE captured now — it's a
  query-layer addition later, not a new instrumentation gap.
- Standby vs hibernate not distinguished (Windows doesn't expose it to user
  mode via PBT_APMSUSPEND).

Bug found and fixed during this phase:
- Same class of bug as Phase 3's BatteryPersistenceBridge race: nothing new
  broke, but SessionMonitoringService.StartAsync proactively calls
  OnBatteryUpdatedAsync() once at startup for the same reason (hosted services
  start sequentially; whatever BatteryMonitoringService already read before
  Sessions subscribed must still be picked up).

PHASE 7 — Application usage (complete)
------------------------------------------------------------
Per-application battery attribution. Windows only exposes MEASURED per-process
energy via SRUM (needs admin; spec S23 forbids requiring elevation), so per-app
energy is a PERMANENT model — AppEnergyV1. Built like Phases 5/6: pure logic in
Core, a promoted infra-sibling orchestrator (Core-only ref), a Data write queue,
a 1 Hz-coalesced view model. ProcessSample + ApplicationUsage tables already
existed verbatim from V001, so NO migration was needed.

What shipped:
- Core.Processes (pure): ProcessCpuCalculator (delta CPU, "% of one core",
  core-capped, pid-reuse guard), ProcessGrouping + ProcessGroupingTable (path ->
  name -> fallback; Default built-in; browser renderer/GPU children fold in),
  BaselineEstimator (EWMA of idle draw split by screen state; conservative
  default + forced Low confidence until 20 idle samples/state), AppEnergyEstimator
  = "AppEnergyV1": E_total -> E_apps = E_total - E_baseline -> weighted share_i;
  shares sum to 100% of the attributable budget; baseline is a distinct entry;
  tail beyond top-N collapses into one "Other" row.
- New Core models/enums: ProcessRawSample, AppUsageEntry, AppEnergyAttribution,
  ProcessSampleBatch/Record, AppEnergyWeights/AppActivity, AppEnergyConfidence,
  ProcessWindow; interfaces IProcessEnumerator, IProcessMonitoringService,
  IProcessSampleWriteQueue; ProcessMonitoringSettings config category (weights,
  top-N, idle floor, default baseline — configuration, not code constants).
- ProcessMonitoring project: PROMOTED from the ModuleMarker stub to
  net10.0-windows, Core-only ref. SystemProcessEnumerator (Process.GetProcesses,
  cumulative CPU time, working set; foreground pid via one LibraryImport; exe
  path + start time cached by (pid,startTime); protected processes skipped).
  ProcessMonitoringService (hosted, own 10s timer): delta CPU -> group ->
  skip-when-idle (screen off + low CPU) -> resolve E_total from
  IBatteryMonitoringService (discharge + Measured/Calculated power only) ->
  BaselineEstimator -> AppEnergyEstimator; 1h tick buffer; GetRanking(window)
  averages CPU over the window at the latest tick's draw; persists per-application
  rows. Cold-start tick publishes nothing. ProcessGroupingTableLoader merges an
  optional %LocalAppData%\BatteryIntelligence\process-groups.json.
- Data: ProcessSampleRow/Repository, ProcessSampleWriteQueue (200/30s/flush/1000
  cap; no BatteryDevice FK on this table). DatabaseMaintenanceService gained the
  idempotent daily ApplicationUsage rollup (only days before today; __baseline__
  excluded) + ProcessSample retention (rolled-up + open-session guards; baseline
  rows on plain age cutoff). ProcessSampleRowCount on the Diagnostics DB facts.
- App: AppUsageViewModel (window + sort selectors, ranked rows with share bars,
  a distinct baseline slice, confidence line, on-AC state, permanent Estimated
  badge). Views/AppUsagePage.xaml rebuilt in the card language (placeholder gone)
  with a "How this is estimated" link to About. Dashboard "Application Usage"
  card wired to the top app. About page: full AppEnergyV1 methodology (spec S55).

estimated / 63% share, code 22% / 3,415 mW, the app itself 2.8%, baseline

Key deviations (see docs/roadmap.md Phase 7 for the full list):
- GPU + I/O per-process weight are configured but not observed (need ETW/admin) —
  attribution is CPU + foreground weighted; the full AppEnergyV1 formula stays.
- Application icons not extracted — monogram tiles; the metadata-cache seam is
  in place to add them later.
- Baseline is a simplified EWMA split, not a least-squares regression.
- ProcessSample rows are per-application (ProcessId 0), not per-process — nothing

- CPU% is "% of one logical processor" (sum can exceed 100); cores only cap a

- Grouping table = embedded C# default + optional JSON override, not a DB table.
- Window selector: "Last hour" / "This session" only (24h/7d/30d need Phase 11).
- No V002 migration — both tables exist from V001; backup-before-migration stays
  untested until a real schema change ships.
- Attribution is system-wide, not per-battery (one process context).

Key deviations (see docs/roadmap.md Phase 8):
- Degradation trend uses a Theil-Sen median slope, not OLS — one anomalous
  full-charge reading otherwise swings the line, and the exit criterion is
  "noise does not move the trend".
- StatisticsEngine computes from BatterySession rows directly, not the
  DailyStatistics tier (sessions are never pruned). The SampleHour + DailyStatistics
  producers still ship (close R-067); Phase 11 (History) consumes the tiers.
- DailyStatistics temperature + end-of-day-health columns left null for now.
- Charging quality is computed + unit-tested but has no dedicated card yet.
- RuntimeEstimationService is a separate hosted service, not folded into Power.
- Statistics window selector: Today/7d/30d/Lifetime (custom range is Phase 11).
- No V002 migration — every table used exists from V001.
